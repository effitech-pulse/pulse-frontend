# Справка в приложении

Пользовательские тексты находятся в двух JSON-файлах и входят в сборку приложения:

- [Руководство пользователя](../../src/content/help/user-guide.json) — 13 статей с действиями в интерфейсе.
- [Бизнес-процессы](../../src/content/help/business-guide.json) — 8 статей о назначении, ответственности и разборе результатов.

Дата сверки содержания: 08.11.2026. Дата в JSON означает проверку содержания,
а не дату обновления модели, источников или результатов расчётов.

## Формат содержания

Корневые поля: `id`, `title`, `description`, `updatedAt`, `articles`.
`id` совпадает с именем файла: `user-guide` или `business-guide`.
`updatedAt` — дата сверки в формате `YYYY-MM-DD`.

Статья содержит `id`, `title`, `summary`, `keywords`, `sections`.
ID статьи — стабильная строка ASCII в kebab-case, уникальная внутри руководства.
Поисковые слова — русские варианты названий действий и понятий; допустимы
употребляемые в интерфейсе сокращения и форматы, например ID Pulse, CSV, XLSX.

В секции обязательное поле `heading`; содержимое задаётся непустыми массивами
`paragraphs`, `steps`, `bullets`, `links`. Поля без содержимого опускаются.
Ссылка имеет только `label` и `to`. Текст — plain text: без Markdown, HTML,
встроенных обработчиков и персональных данных.

Адрес статьи: `/help/<guideId>/<articleId>`. Сохраняйте ID при переименовании
заголовка: на статьи уже могут ссылаться другие статьи или пользователи.
Для удаления статьи сначала найдите ссылки на её ID и согласуйте замену.
Не создавайте ссылки на вымышленную скважину, событие, сотрудника или расчёт.
Ссылки на рабочие разделы должны вести на существующие статические маршруты
из `src/router.tsx`; доступ к данным и действиям по ним остаётся серверным.

## Как актуализировать

1. Найдите изменившийся сценарий в исходниках страницы, её компонентов и
   используемых API. Сверьте названия кнопок и вкладок, права, режим функции,
   условия сохранения, состояния ошибки и недостаточности данных.
2. Проверьте сценарий в версии приложения, для которой выпускается справка.
   Наличие экрана в Figma, старом README или другом checkout не доказывает
   готовность функции в выпускаемой версии. Зафиксируйте расхождения в
   рабочей задаче; не описывайте неподтверждённый результат как доступный.
3. Обновите затронутые статьи обоих руководств и связанные поисковые слова.
   Разделяйте подтверждённое поведение, ограничения и целевые возможности.
   При изменении политики использования данных направляйте читателя к
   действующей политике в приложении: не копируйте её сроки и получателей
   в справку без необходимости.
4. Обновите `updatedAt`, проверьте JSON и все ссылки. Прочитайте полный
   сценарий от начального выбора до подтверждения результата сервером.
5. Выполните `npm test`, `npm run lint`, `npm run build` из корня checkout.
   В браузере проверьте оглавление, поиск, статью по прямому адресу,
   переходы между руководствами и доступность длинного текста на узком экране.
   Результаты проверок сохраните в рабочей задаче, а не в product checkout.

## Смысловые правила

- Прогноз за 7–14 суток — цель; текущая оценка не гарантирует точную дату отказа.
- Риск окна, накопленный ярус, качество данных и заключение технолога независимы.
  Низкий последний риск сам по себе не снимает ярус.
- Нет данных или оценки — не норма и не нулевой риск.
- Простой с валидным нулём отличается от пропуска и маркера неисправности.
  Уставка отличается от измерения; заполненный признак — от измеренного.
- Не обещайте работающую классификацию всех 13 типов отказов.
  Для #2/#8/#9 на старте предусмотрен общий класс отложений и засорения.
- Синтетический сценарий не подтверждает промышленное качество и не разрешает
  загрузку реальных файлов в ограниченный пилот.
- Прочтение уведомления, заключение по результату, факт отказа, выполненная работа
  и завершение задания — отдельные действия и записи.
- Название роли не заменяет разрешение и область данных. Не обещайте
  автоматическое сохранение или доступность без подтверждения соответствующего пути.
- Производственное решение принимает человек по регламенту предприятия.

Тексты не устанавливают новые требования, SLA или сроки реакции.
Изменения продуктового процесса передаются владельцу продукта через
координатора; справка описывает принятое и проверенное поведение.
